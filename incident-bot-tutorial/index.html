On-Call 自動根因分析 · Field Manual

當警報在半夜響起，
讓 Claude 先進事故室

這份手冊教你從零打造一條全自動 pipeline：OpenObserve 偵測到生產異常 → Cloudflare Worker 轉信 → GitHub Actions 拉下程式碼 → Claude 跨 repo 找根因 → 回貼 Slack。附上如何把 Claude API 換成訂閱型 Claude Code，以及怎麼調出「有溫度」的回覆。

🕵️ 角色 資深 SRE 偵探 ⚡ 觸發到回覆 1 秒 dispatch · 10–15 分分析 🧩 元件 OpenObserve · CF Worker · GitHub · Claude · Slack 💰 單次 ~$0.3 API · 或訂閱吃到飽
01

系統總覽

五個角色各司其職。把它想成醫院急診：警報器發現病人倒下，警衛驗證身分放行，工廠流水線安排偵探，偵探查完把診斷交給家屬群組。下圖標出每一段實際傳什麼、用什麼認證。

02

03

建置路線圖

不要一次全做。這條 pipeline 是分三階段長出來的——每一階段都能獨立驗證、獨立上線，前一階沒通不要進下一階。

P0ANALYZE

先搞懂事故長怎樣

拿一次真實 incident 的 15 萬條 error log，反覆迭代聚合 SQL，把 90% 落在「其他」的雜訊，拆成幾個有意義的錯誤桶。這一步不寫任何自動化，純粹是把「什麼訊號代表什麼」搞清楚。

  • 用 DataFusion SQL 的 LIKE + CASE WHEN 分桶
  • 找出 5 條真正該告警的 lane：outage / 錢包 / 欠款 / 連鎖 / 資料完整性
✔ 已定義 5 條 alert lane
P1ALERT

接上 OpenObserve → Slack 告警

把 P0 找到的 5 條 lane 做成 OpenObserve alert，命中就發 Slack。先讓「有事會叫」這件事跑起來，還不牽扯 Claude。

  • 每條 alert = 一段 SQL + 門檻 + silence + destination
  • P0/P1 分級：財務/資料類 1 筆就叫，規模類要上量
✔ 5 條 alert 上線，Slack 通了
P2ANALYZE+

接上 Claude 自動根因分析

加 Cloudflare Worker 繞過 OpenObserve 的 webhook bug、建 GitHub App、寫 workflow 讓 Claude 進 repo 找根因，最後回貼 Slack thread。這是整個系統「會思考」的部分。

  • CF Worker proxy + GitHub App（不綁人、不過期）
  • 跨 repo checkout（target + 上游），Claude grep 真實 diff
  • 3 份平行分析 + 綜合，誠實標信心度
✔ 端到端跑通，繁中 TL;DR 回貼
04

元件設定教學

四個要親手設定的元件。每張卡片給你「關鍵參數」加「最小可動程式碼」——照著填就能跑，細節再看官方文件。

Component · 偵測

👁️OpenObserve Alert

一條 alert 就是「一段 SQL + 三個刻度」。SQL 數某類錯誤的 count，三刻度決定多久看一次、超過多少叫、叫完多久閉嘴。

period往回看 5 分鐘
frequency每 1 分鐘檢查
thresholdcount >= 10 才 fire
silencefire 後靜音 30 分
-- 錢包扣款失敗告警
SELECT COUNT(*) AS cnt
FROM "log_prod_game_server"
WHERE loglevel = 'Error'
  AND message LIKE '%Credit fail%'
關鍵財務/資料類設 >=1 就叫（1 筆玩家沒收到錢就是糾紛）；規模類設 >1000（低於是雜訊）。門檻不同才分得出「人受害」跟「系統大爆」。
Component · 轉信

🛡️Cloudflare Worker

接 OpenObserve 的 webhook，驗暗號、用 GitHub App 簽 JWT 換 installation token，再 POST repository_dispatch 觸發 workflow。

export default {
  async fetch(req, env) {
    // 1 · 驗 shared secret
    if (req.headers.get('X-OpenObserve-Secret')
        !== env.OPENOBSERVE_SECRET)
      return new Response('Forbidden',{status:403});

    // 2 · App 私鑰簽 JWT → 換 installation token
    const jwt = await createJWT(
      env.GITHUB_APP_ID, env.GITHUB_APP_PRIVATE_KEY);
    const { token } = await (await fetch(
      `https://api.github.com/app/installations/
      ${env.GITHUB_INSTALLATION_ID}/access_tokens`,
      { method:'POST', headers:{
        Authorization:`Bearer ${jwt}` }})).json();

    // 3 · 觸發 workflow
    const gh = await fetch(
      `https://api.github.com/repos/
       ${env.GITHUB_REPO}/dispatches`, {
      method:'POST',
      headers:{ Authorization:`Bearer ${token}` },
      body: JSON.stringify({
        event_type:'incident-detected',
        client_payload: (await req.json()) })});

    return new Response(null,
      { status: gh.status===204 ? 202 : 502 });
  }
};
部署：npx wrangler deploy（免費層每天 10 萬次）

Component · 回覆

💬Slack Bot

用 Bot Token（chat:write）把報告貼回 thread。先發一則「分析中…」拿 thread_ts，分析完再用它回貼——把告警和分析串成同一串對話。

scopeschat:write · chat:write.public
tokenxoxb-…
格式Slack mrkdwn（非標準 md）
# 先發「分析中」拿 thread_ts
resp=$(curl -sS -X POST slack.com/api/chat.postMessage \
  -H "Authorization: Bearer $SLACK_BOT_TOKEN" \
  -d '{"channel":"C0…","text":":mag: 分析中…"}')
ts=$(echo "$resp" | jq -r .ts)

# 分析完回貼同一 thread
curl -sS -X POST slack.com/api/chat.postMessage \
  -H "Authorization: Bearer $SLACK_BOT_TOKEN" \
  -d "{\"channel\":\"C0…\",\"thread_ts\":\"$ts\",
      \"text\":\"$report\",\"mrkdwn\":true}"
格式陷阱Slack 用 mrkdwn 不是標準 markdown：粗體是單顆 *星*、沒有 ## 標題、不吃表格。要在 prompt 裡叫 Claude 直接輸出 mrkdwn，用 emoji 當標題。
05

Claude 怎麼被觸發、怎麼分析

workflow 不是直接叫 API 問一句話，而是把 Claude 當成「能進 repo 辦案的偵探」。三個設計讓它更準：跨 repo 追溯、強制看真實 diff、跑三次投票收斂。

組 prompt：餵給偵探的卷宗
事故時間窗、OpenObserve top 30 錯誤桶、近 7 天 commit、上游服務清單，全部塞進一份 prompt。附上「最容易被 log 漏看的 6 類根因」清單（序列化 tag、schema migration、cache 舊資料…）。
跨 repo 追溯：症狀在下游、真因在上游
GameServer 的 log 大爆，真因常是上游 Valhalla 一個部署。Workflow 把上游 repo 也 clone 下來，用 --add-dir 讓 Claude 能同時 grep 兩邊，並比對「tag 建立時間是否落在事故窗 ±2 小時」。
強制看真實 diff：禁止用猜的
每個嫌疑 commit 都必須跑 git -C repo show <sha> 看真實 diff，禁止根據 commit 標題或「修好後的程式碼」反推。命令失敗就老實寫「無法判定」，不准編造。
三份平行 + 綜合：把不確定性攤開
同一份 prompt 平行跑 3 次（LLM 探索路徑隨機，可能挑不同嫌犯），再用第 4 次 Claude 綜合：3 份一致→信心高；2:1→標多數+附異議；全不同→誠實標「⚠️ 多個 plausible 嫌犯」讓人裁判。
最終產出一則繁中 Slack 訊息，開頭三行就是 CTO 要的：發生什麼 / 根因（含 file:line）/ 立即做。後面才是證據鏈、真實 diff 摘錄、殘留待處理項。整體壓在 6000 字內，10 秒掃完。
06

把 Claude API 換成訂閱型 Claude Code

現在 workflow 用 ANTHROPIC_API_KEY，是按 token 計費。如果你已經有 Claude Pro / Max 訂閱，可以改用「訂閱額度」跑同一支 CLI——寫成一個 Python 服務，就像常見的 slack-claude-bot，只是不吃 API 帳單，改吃訂閱。

實作紀錄 · Architecture C 這一節的想法已經做成一個可跑的 demo：OpenObserve → Slack → 本地 Python + 訂閱 Claude + GitHub → 回貼 Slack（拉取式、不需 24/7 對外主機）。架構、進度與觸發方式見 Architecture C — 訂閱制本地 Demo 實作紀錄 ↗。

現況Claude API（按量計費）

  • 認證：ANTHROPIC_API_KEY
  • 計費：每百萬 token 計價，用多少付多少
  • 適合：自動化 / 無人值守 / 高併發（官方支援）
  • 單次事故約 $0.3–3，量大會累積

目標訂閱型 Claude Code（吃訂閱額度）

  • 認證：CLAUDE_CODE_OAUTH_TOKEN（claude setup-token 產生）
  • 計費：固定月費，額度內不另計；有用量上限
  • 適合：個人 / 小團隊 / 內部工具
  • 綁人類帳號、token 會過期要 rotate

① 拿到訂閱 token

在你本機（已登入 Claude Pro/Max 的環境）跑一次，產生一個長效 OAuth token。這個 token 讓 CLI 走訂閱額度而不是 API 帳單。

# 產生訂閱 OAuth token（會開瀏覽器授權）
$ claude setup-token
# → 輸出 sk-ant-oat… 這一串就是 CLAUDE_CODE_OAUTH_TOKEN

# 驗證：設了它、且「不」設 ANTHROPIC_API_KEY，CLI 就走訂閱
$ CLAUDE_CODE_OAUTH_TOKEN=sk-ant-oat… claude --print "你好，你在用訂閱嗎"

② 寫成 Python Slack Bot（訂閱版）

跟常見的 slack-claude-bot 一樣用 slack_bolt 收 Slack 事件，差別只在：分析時用 subprocess 呼叫 claude CLI，環境只放 OAuth token、不放 API key——CLI 就自動走訂閱。

incident_bot.py
import os, subprocess
from slack_bolt import App

app = App(token=os.environ["SLACK_BOT_TOKEN"])
OAUTH = os.environ["CLAUDE_CODE_OAUTH_TOKEN"]  # 來自 claude setup-token

def analyze(prompt: str, repo: str) -> str:
    # 關鍵：env 只給 OAuth token，不給 ANTHROPIC_API_KEY
    #      → claude CLI 走「訂閱額度」，不計 API 費用
    env = {**os.environ, "CLAUDE_CODE_OAUTH_TOKEN": OAUTH}
    env.pop("ANTHROPIC_API_KEY", None)
    r = subprocess.run(
        ["claude", "--print",
         "--add-dir", repo,
         "--allowed-tools", "Read,Grep,Bash(git:*)"],
        input=prompt, capture_output=True, text=True,
        env=env, timeout=1800)
    return r.stdout

@app.event("app_mention")
def on_mention(event, say):
    ts = say(":mag: 我接手了，先看資料…")["ts"]
    report = analyze(build_prompt(event["text"]),
                     "/srv/repos/GameServer")
    say(text=report, thread_ts=ts)   # 回貼同一 thread

if __name__ == "__main__":
    app.start(port=3000)
用訂閱跑自動化前，先確認這幾件事 ① 額度上限：訂閱有 usage cap，衝太快會被限流，不適合高併發無人值守。② token 會過期：setup-token 產的 token 需定期 rotate。③ 服務條款：把個人訂閱拿去跑純自動化服務前，確認符合當前 Anthropic ToS——真的要大量無人值守，API 才是官方路徑。個人 / 小團隊內部工具用訂閱最划算。

③ 調出「有溫度」的回覆——情緒價值就是 prompt

值班同事半夜被叫醒、腎上腺素飆高。同樣的根因，用不同語氣講，感受天差地遠。把「人設 + 語氣規則」寫進 system prompt，Claude 就會用那個口吻回。這段是純文案工程，不用改任何程式。

persona.txt（注入 prompt 開頭）
# === 人設 ===
你是資深 on-call SRE「老偵探」。沉穩、不指責、先安撫再分析。
你的頭像是個戴眼鏡的白髮老紳士——講話就是那個氣質。

# === 語氣規則 ===
1. 開頭一句話讓值班同事安心：「我接手了，先看資料」
   —— 不要一上來就丟一堆錯誤數字砸人。
2. TL;DR 三行講完：發生什麼 / 根因 / 立即做。
3. 有把握寫把握，沒把握明講「需人工裁判」——
   不要用「可能、大概、也許」連續堆疊製造假象。
4. 絕不指責是誰的 commit 造成的；只講「這個變更 +
   舊資料 = 這個結果」，對事不對人。
5. 結尾一定給「下一步」，不要只丟結論讓人自己想。
6. 全程繁體中文，識別子（file:line / SHA）保留原文。

🥶 沒調語氣（冷冰冰）

  • ERROR count: 15,510. NullReferenceException at line 183. Root cause: commit 2c9d309.
  • → 正確但沒溫度，半夜看了更焦慮，也不知道先做什麼。

🕵️ 調過語氣（有溫度）

  • 我接手了，先別慌。這波是上游一個部署帶出的舊資料不相容，範圍清楚、可控。
  • 立即做：確認 Valhalla 目前版本，其餘我已整理在下面，你先喝口水。
  • → 一樣的事實，先接住情緒再給行動。
一句話總結這節認證換 token（API key → OAuth token）決定誰付錢；persona prompt 決定什麼口吻。兩件事互相獨立——你可以訂閱制 + 冷語氣，也可以 API + 暖語氣，自由組合。
