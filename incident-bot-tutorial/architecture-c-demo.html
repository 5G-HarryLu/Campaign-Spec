Architecture C · 訂閱制本地 Demo · 實作紀錄

不架伺服器，
讓本地 Claude 去 Slack 撈事故

OpenObserve 告警 → Slack → 本地 Python（拉取）→ 本地 claude（吃訂閱）＋ GitHub → 回貼 Slack thread。這是主手冊 Architecture A（Serverless + API） 之外、專為「沒有 24/7 對外主機、想用訂閱額度」設計的第三條路。本頁記錄實際 demo 的架構、進度與觸發方式。

🔌 拉取式 出站輪詢，免對外主機 💳 吃訂閱 claude CLI，非 API 🧩 組成 OpenObserve · Slack · Python · Claude · GitHub 🔒 與生產隔離
01

這是什麼 / 為什麼是這個架構

主手冊的正式管線（Architecture A）已在生產環境上線：OpenObserve → Cloudflare Worker（harry-lu）→ GitHub Actions → Claude API → Slack。它需要一個對外的 serverless 端點、GitHub App、以及按量計費的 API key。

本 demo 走 Architecture C，因為兩個限制：沒有 24/7、對外的主機 可以接 webhook；想用個人 Claude 訂閱額度而不是 API 帳單。解法是把「推」改成「拉」：本地機器只做對外連線，主動去 Slack 撈告警。Slack 變成一個佇列——OpenObserve 一定送得進 Slack，告警就停在頻道裡等本地 bot 下次執行時撈走。機器關機也不會漏，開機再補跑即可。不需要對外 IP、不需要打洞、不需要常駐伺服器。

03

OpenObserve 通知裡放多少內容？

通知內容取決於 destination / template，而且有實際的大小取捨。目前用原生「Slack」型 destination，送出的是很薄的訊息——測試證明整包幾乎只有告警名稱：🚨 Alert: Test Alert - High CPU Usage，沒有錯誤明細、沒有時間窗、沒有筆數。所以現況下 bot 必須回頭查 OpenObserve 才拿得到細節。

OpenObserve 能透過 template 放進更多變數：alert_name、stream_name、alert_count、alert_operator/threshold、alert_start_time/end_time、alert_url…以及最關鍵的 rows（實際命中的 log 記錄，全部 stream 欄位都是變數）。rows 可能很大，所以用 {rows:N}／{var:N} 限制筆數與字串長度。

模式訊息內容優點缺點
薄觸發 + bot 查 OO
（建議）		alert_name + 時間窗 + 筆數Slack 乾淨；bot 依需要抓時間窗／聚合；能吃大事故需要 OO API token（待辦 c）
厚訊息 {rows:N}直接嵌入命中的 log rows自帶內容；免 API token被截成 N 筆；洗版；大事故失真
建議 · 與主手冊一致採混合式：通知只當輕量觸發，帶足夠資訊（alert_name + alert_start_time/end_time + alert_count），由分析端回頭查 OpenObserve 撈真正的 rows／top 錯誤桶。能吃大事故又不洗版。實務上：(1) 觸發訊息改用含時間窗的 template（我們的 slack_incident_demo 已含，只是原生 Slack 型不套用它，需改用 Custom 型），(2) 給 bot OO API token（待辦 c）去抓明細。
04

如何觸發一次 Demo flow

前置：SLACK_BOT_TOKEN 已填入 ~/github/incident-bot/.env（xoxb-…），本機 claude CLI 已登入訂閱帳號。

讓一則告警進到 #incident-demo（三選一）
  • 最快（測試按鈕）：OpenObserve → Settings → Notification Destinations → slack-incident-demo → Test。送一則 🚨 Alert: … 進頻道。
  • 接近真實（clone alert）：見待辦 (b)，clone 一條 game-server alert、destination 只留 slack-incident-demo、存檔；條件命中即自動送信。
  • 手動：對 #incident-demo 的 incoming webhook curl 一則 {"text":"..."}（webhook URL 屬機密，勿外流）。
跑 bot 撈走並分析
# 進專案
cd ~/github/incident-bot

# 處理一次就結束（適合手動 / cron / launchd）
./.venv/bin/python incident_bot.py --once

# 或機器開著時持續輪詢
./.venv/bin/python incident_bot.py
看結果
回到 Slack #incident-demo，展開那則告警的 thread：bot 先回「🔍 我接手了，先看資料…」，接著貼上繁中根因報告（TL;DR 三行：發生什麼 / 根因 / 立即做）。
分析深度取決於資料源只有告警文字時 → 給方向與下一步；接上 (a) repo → 能指到 file:line / commit SHA 並看真實 diff；接上 (c) → 帶真實 error log 佐證。
