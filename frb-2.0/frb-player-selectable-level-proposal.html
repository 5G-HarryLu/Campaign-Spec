FRB Player-Selectable Level 設計提案

玩家自選「衝哪個 level」與「何時使用」 · 對齊 msg-center claim 流程（popup + inbox + info card） · 更新 2026-06-05
Page 1 · Overview

背景與目標

為什麼要改，以及這次定案的方向。

現行模型：循序累積佇列

  • ThresholdChecker.Check 只回傳「第一個已達標」的 level（累積門檻，其餘卡關）。
  • 一次只能有一張活躍票（Pending/InUse 會 block accumulation）。
  • 發票即被消耗（Pending → InUse 首 spin 自動轉移），玩家無選擇使用時機的權利。
🎯 目標：讓玩家自行選擇衝哪個 level、自行選擇何時開玩。獎勵透過 msg-center（popup + inbox）通知，玩家可「馬上使用 PLAY NOW」或「稍後使用 PLAY LATER（留 inbox 之後領）」。

Page 2 · Big Picture

新模型總覽

下注 → 累積 → 每 level 達標 → 即建 Pending 票並通知 → 玩家自選馬上/稍後使用。

起點/動作 判斷 建票/通知 流程
圖 2-1　新模型端到端主流程（每 level 達標即各自建票進 inbox）

三個關鍵差異

  • 達標即建票：winning 當下就建 Pending 票並寫 outbox，inbox 直接讀該票顯示 bet × 剩餘次數、過期、game_name。
  • 領取 ≠ 使用：Pending（在 inbox 待領、不阻擋累積）與 InUse（claim 後開玩）分離。
  • 累積達標、一次全產出：累積門檻沿用現行；達標到 L3 時 L1~L3 同時各自產出 winning 票，玩家各自獨立使用（不再循序 gating）。
🧮 範例：門檻 L1=10、L2=20、L3=30（累積判定，沿用現行）。玩家直接下注 100，一次達標到 L3。
· 現行 只先給 L1，用完才給 L2、再用完才給 L3（一次一張、卡關）。
· 新做法 L1~L3 同時全部產出，inbox 同時看到 3 張，玩家挑哪張先用、何時用。

Page 4 · State Machine

票券狀態機（沿用既有，語意更新）

不新增 Granted，直接用 Pending 當「在 inbox 待領」態，只更新語意。

圖 4-1　新版票券 FSM（綠=正常終態，紅=過期）

狀態定義

值狀態語意claimed_at
1Pending
（未領取）		達標已建、在 inbox 待 claim、不阻擋累積NULL
1Pending
（已 claim 未開始）		PLAY NOW 已 claim、尚未首 spin已設
2InUse首 spin 後開玩中已設
3Completed全數玩完已設
4EarlyCompleted達 max payout / 手動結束已設
5Expired待領逾期 或 使用中逾期—

無 Granted、無 Activated、無 PendingClaim/Claimed；狀態值維持 1..5。「未領取」與「已 claim 未開始」同為 Pending，靠 claimed_at 是否為 NULL 區分（claim = PLAY NOW only）。

語意變更重點

  • 舊 Pending 阻擋累積、首 spin 自動使用。
  • 新 Pending 不阻擋累積、需玩家 claim 才使用。
  • 不新增 Granted：收斂回 Pending，降低狀態機複雜度。
  • 不需 Activated：玩家可同時多開不同遊戲、campaign 可同時指定多遊戲，不能靠同 session 後踢前；改全面以 FSM + CAS（DB exclusive row lock）保護 claim，affected-rows 檢查即權威，無需鎖 session（見 Page 9 情境）。
Page 5 · Data Structures

資料結構變更

DDL、Threshold、PlayerProgress、Redis 庫存索引。

free_round_bonus_ticket_details DDL

票券於 winning（達標）時建立，故 created_at = 達標時間。

ALTER TABLE `free_round_bonus_ticket_details`
  ADD COLUMN `claimed_at` timestamp(3) NULL -- 玩家 claim 時間（PLAY NOW only；NULL=未領取，NOT NULL=已 claim 未開始）
  ADD COLUMN `expired_at` timestamp    NULL; -- 領獎期間到期 = created_at + ticket_validity_days

ALTER TABLE `free_round_bonus_ticket_details`
  ADD KEY `idx_status_expired_at` (`status`, `expired_at`); -- 過期掃描

-- 維持 status 1..5（不加 PendingClaim/Claimed）；不需 version 欄位。
-- 玩家可同時多開不同遊戲、campaign 可指定多遊戲，無法靠同 session 後踢前，
-- 故全面以 FSM + 「狀態條件式 UPDATE」(CAS, DB exclusive row lock) 保護：
--   claim(PLAY NOW): UPDATE ... SET claimed_at=now WHERE id=? AND status=Pending AND claimed_at IS NULL  → affected=1
--   首 spin:         UPDATE ... SET status=InUse   WHERE id=? AND status=Pending                          → affected=1
「每 level 終身一張」由既有 uk_ticket_level (ticket_id, level) ＋ 父票 uk_campaign_operator_member 天然保證，無需新增唯一鍵。
max_payout_cents / reward_count / game_id / rate / bet 於建票（達標）時凍結寫入；其中 bet 由 by-level 取得，沿用既有 campaign_operator_game_chips（已含 level 欄），threshold_cents 不變（累積）。

ThresholdChecker 改寫

// 舊：只回第一個已達標 level（其餘卡關）
// 新：回傳「所有」已達標未建票 level（累積門檻不變）
GetNewlyWonLevels(progress, thresholds) =>
  thresholds.OrderBy(t => t.Level)
   .Where(t => !progress.HasWon(t.Level))
   .Where(t => progress.TotalBet >= CumulativeThreshold(t.Level)) // Σ 1..N 沿用現行
   .Select(t => t.Level);

CalculateActualThreshold 累積邏輯保留；threshold_cents 語意不變，只是 Check 改為一次回傳所有已達標 level（移除循序 gating）。

PlayerProgress 欄位

舊新
level_N_qualifiedlevel_N_won（達標已建票冪等鍵）
level_N_qualified_at_bet保留（稽核）
level_N_ticket_id建票時寫入
level_N_notified保留（winning 去重）

claim/使用狀態存在票券本身（status/claimed_at），progress 只負責建票冪等。

Redis 庫存索引（新增）

Key:  frb:inventory:{campaign_id}:{operator_id}:{member_id}   (Hash / ZSet)
Val:  detail_id -> { level, status, created_at, expired_at,
                     bet, reward_count, used_rounds, max_payout_cents, game_id }
  • 建票（達標）時 HSET；狀態轉移 / 過期時同步更新或移除。
  • frb:ticket:{detail_id} 既有單票 hash 沿用（GameServer 讀取）。
  • inbox 即時狀態（used_rounds/剩餘/過期）由 FRB Read API 查 Redis 回即時值（Keen Q10 已定案 A）。此 API 為 free-round-bonus campaign 新增的 web API（沿用「提供給 PlatformApi 呼叫」的既有模式）。
Page 6 · End-to-End Flow

端到端流程（swimlane）

玩家 / FRB Service / msg-center / GameServer 四方協作。

圖 6-1　達標 → 通知 → claim → 使用 的四方協作

① 達標 → 建票 + outbox

BetEventProcessor：

  • 累積 total_bet（不阻擋）。
  • GetNewlyWonLevels 取新達標 level。
  • 每 level 建 Pending 票，凍結 game_id/rate/bet/reward_count/max_payout，設 expired_at。
  • uk_ticket_level 撞鍵 → 冪等略過。
  • 寫 frb:inventory ＋ 發 winning outbox。

② claim / ③ 使用 / ④ 過期

  • PLAY NOW：claim+跳轉，狀態條件式 UPDATE（WHERE status=Pending）設 claimed_at，帶選定票券資訊到 GameServer，進遊戲首 spin → InUse。
  • PLAY LATER：票維持 Pending 留 inbox，之後點擊使用同上。
  • 允許同時多張 InUse：玩家在 inbox / PLAY NOW 自行選定要用哪張 level 票，GameServer 以該票遊玩、每局寫 mapping（frb_ticket_detail_id）。
  • 移除 TryGrantNextLevelTicketAsync 循序授予。
  • 過期：TicketExpirationBackgroundService 改掃 detail 級 expired_at（待領+使用中）。

info card & reminder & payload

  • info card：now BETWEEN created_at AND expired_at 且 Pending/InUse → 顯示。FRA 無此線。
  • reminder：整體移除 reminder 機制（含活動結束倒數與斷線重進 FRB 的 reminder/轉導）。
  • winning payload：campaign_name / game_id / game_name / bet_cents / reward_count / max_payout_cents / expires_at / level。

Page 8 · Config & API

bet by level & API 草案

bet by level

  • 資料層已就緒：campaign_operator_game_chips 已新增 level 欄（key = campaign_id, operator_id, game_id, level），bet 即 by-level 面額。
  • 取值：建票（達標）時呼叫 GetGameChipsConfigByLevelAsync(camp, op, game, level)，取該 level 的 bet 凍結寫入 detail bet。沿用既有 GameChipsConfig + level，不新增 campaign_frb_level.bet_cents。
  • fallback：level=0 列為 legacy（建於 level 欄存在前），舊 RPC 無 level 參數時走此列。

API 草案（FRB Service）

MethodPath說明
GET/api/frb/inventory列出玩家庫存票（level/狀態/bet/剩餘/過期/game）— 供 inbox & info card
POST/api/frb/claimPLAY NOW only：{ticketDetailId, idempotencyKey} → CAS 設 claimed_at（WHERE status=Pending AND claimed_at IS NULL）。PLAY LATER 不呼叫此 API，票留 inbox 維持 Pending。
  • 建票由 winning 流程自動完成，無對外建票 API。
  • claim 防重：idempotencyKey（擋雙擊/重送）+ 狀態條件式 UPDATE（WHERE status=Pending，DB exclusive row lock 保證只成功一次）。玩家可同時多開不同遊戲、campaign 可指定多遊戲，不靠同 session 後踢前，全面以此 FSM + CAS 保護；不需 version 欄位。
  • 供 msg-center callback，對齊 Tournament RewardClaimService 設計。

凍結策略

  • 於 winning（建票）時 凍結當下配置寫入 detail（bet 取自 campaign_operator_game_chips by-level；threshold 取自累積門檻配置）。
  • 建票後配置變更：已建票維持原值；未達標 level 套新值。
  • 「換遊戲使用」屬另案，本提案先固定建票當下 game_id。

Page 11 · Risks & Roadmap

風險未決 & 實作階段

風險與未決項

  1. 門檻無遷移：累積門檻語意與現行相同、threshold_cents 不變，無數值遷移風險。真正的行為改動是移除循序 gating（一次全產出）。已定案 允許玩家同時持/開多張票；玩家透過 inbox / PLAY NOW 選定要用哪張 level 票，帶票券資訊到 GameServer 使用（非 GameServer 自選），每局寫 mapping（frb_ticket_detail_id），used_rounds per-ticket 不受影響。
  2. Pending 語意切換：已定案＝轉新語意。FRB 2.0 為就地優化（非新 campaign type），上線後即無 1.0；因上線時不會有 1.0 在途活動，遷移風險低。仍建議在無在途 Pending 票的窗口部署，並以 rolling-deploy 安全措施（feature flag / 對齊）避免新舊副本並存時發票邏輯不一致。
  3. 成本/負債：已定案 配額以父票計（一玩家＝一張票，與 level 數無關），prize_quantity（玩家數上限）不受全產出影響。僅 max payout 為 per-detail 各 level 累加，屬預算面數字、不影響張數配額。
  4. 票券即時狀態同步（Keen Q10）：已定案＝A. FRB Read API＝ free-round-bonus 新增 web API（沿用提供給 PlatformApi 呼叫的既有模式）。msg-center／PlatformApi 需即時 used_rounds/剩餘/過期 時查此 API（讀 Redis 回即時值）。實作細節待與 msg-center team 對接。
  5. bet by-level：已定案 沿用既有 campaign_operator_game_chips（已含 level 欄、GetGameChipsConfigByLevelAsync 已存在）；不新增 campaign_frb_level.bet_cents。Q7–Q9 的跨遊戲行為仍需產品確認，但 schema 落點已定。
  6. 併發防護已定案：玩家可同時多開不同遊戲、campaign 可指定多遊戲 → 不能依賴同 session 後踢前；改全面以 claim idempotency = FSM + CAS（DB exclusive row lock）保護，affected-rows 檢查即權威。仍 不需 Activated 與 version，idempotencyKey + 狀態 CAS 即足夠。
  7. reminder 整體移除：取消 含活動結束倒數與斷線重進 reminder/轉導；後台 reminder 欄位拔除。
