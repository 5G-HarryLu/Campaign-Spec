FRB msg-center 整合需求與改動分析

需求者：Keen ・ 來源：Notion FRB-msg-center-ticket-bet ・ 文件日期：2026-05-13

1. 需求概述

Keen 提出兩條改動：

  • 訊息系統整合：FRB 通知整合進 msg-center（對齊 Tournament 既有作法），重新切分 popup / inbox。
  • FRB 贈送的 bet 改為 by-level 設定。

1.1 訊息呈現分類（Keen 原文）

純需求視角；技術觸發點與 FRB 動作見 Tab 5.2。

事件呈現方式
Coming Soon（活動即將開始）popup
Welcome（活動開始）popup
Suspend（活動暫停）inbox
Terminate（活動終止）inbox
Winning（提領獎勵）popup + inbox 雙管齊下（inbox 端含 claim 按鈕）
Payout（獎勵結算）popup（msg-center 職責、FRB 不在乎語意）
End Early（活動提早結束）inbox
End（活動自然結束）都不要

1.2 取消的機制

  • Reminder 機制整體取消（含活動結束倒數、斷線重進 reminder/轉導）
  • 自動轉跳遊戲機制取消（理由：獎勵可在 inbox 領取，不再需要強制導流）
  • 後台 reminder 對應欄位一併拔除

1.3 FRB bet 設定改動

bet 改為依 level 設定下注金額，沿用既有 campaign_operator_game_chips（已新增 level 欄，key = (campaign, operator, game, level)）。資料層已 ship（見 §3.1 已定案、§6.2）。

目前後台只允許「不同 level 給不同獎品數量（spins）」，下注金額尚不能 by level；本次改動會把下注金額也納入 level 維度。

隱含的流程改動（從 Keen 對 Payout 的補充推導）
FRB 從「達門檻自動發票券」變為「達門檻通知 → 玩家在 inbox 點 claim → 票券才實際啟用」的 Tournament-style 流程。
這是本次改動裡影響最大的部分，不只是訊息層的調整。

1.4 Winning UI 細節（取自 Figma）

除了上面的訊息分類，Figma 也定義了 winning 的實際互動：

  • Winning popup 上有兩個按鈕：
    • PLAY NOW：直接 claim + 跳轉到綁定的遊戲（一鍵動作）
    • PLAY LATER：不立即 claim，訊息保留到 inbox
  • inbox 列表每筆 FRB 訊息顯示：campaign name、$bet × 剩餘次數、過期時間、PLAY NOW 按鈕
  • 展開狀態顯示：祝賀文案、綁定 game name、過期時間、UNCLAIMED PRIZE 警語

1.5 票券在 inbox 端的生命週期狀態

狀態顯示對應 FRB ticket 狀態
未領取（在 inbox 待 claim）PLAY NOW 按鈕（黃色高亮）Pending=1，claimed_at IS NULL

過期項目按鈕隱藏Expired
FSM 模型（定案 2026-06-05）：沿用 5 個 enum，不加 PendingClaim/Claimed
票券狀態維持既有 1..5（Pending / InUse / Completed / EarlyCompleted / Expired）。Pending=1 本身就是「在 inbox 待 claim」態，不再「阻擋累積」（語意更新）。claim = PLAY NOW only：PLAY NOW 設 claimed_at（CAS WHERE status=Pending）並跳轉；PLAY LATER 不 claim、不動票，留在 inbox 仍是 Pending + claimed_at IS NULL。「已 claim、未開始」與「未領取」靠 claimed_at 是否為 NULL 區分，不需新增 PendingClaim=6/Claimed=7。首 spin → InUse=2。
⚠️ 已 ship 進 TicketStatus 的 6/7 由實作分支移除（含 TicketStatusConverter），本規格不再引用。注意：msg-center 的 InboxEventType/EventType 的 6/7（CampaignWinning/EndedEarly）是另一個 enum，不受影響。
由 Figma 衍生的新核心問題
inbox 上「USED: n / 過期隱藏按鈕」等動態狀態，msg-center 怎麼拿？ 這題是 Q10，方案比較與推薦見 Tab 5.4，問題本身整理在 Tab 3.2。

Outbox 表結構（已對齊 DB）

5.4 票券即時狀態同步（Q10）

Figma 顯示 inbox 要呈現「USED: n」「使用完畢 disabled」「過期隱藏按鈕」等動態狀態，不能只靠單次 Winning event 寫入就完成。三個候選方案：

方案機制優點缺點
A. Read API 推薦 FRB 提供 GET /api/frb/tickets?member_id=&status=，msg-center 在 inbox 開啟時即時查 實作單純、無同步問題；msg-center 不需要維護 read model 每次開 inbox 都打 FRB；流量大時需快取
B. Outbox update events 每次 ticket 狀態變動（claim / 開始使用 / 累積使用 / 過期）寫 outbox msg-center 自治、無查詢延遲 事件量大（每 spin 都可能要寫，需聚合策略）；msg-center 需 read model
C. 訂閱現有 Redis channel msg-center 訂 frb:ticket:in_use / frb:ticket:completed FRB 不需新介面 耦合到 FRB 的 Redis、跨服務不乾淨；違反 D1「全走 outbox」精神

推薦理由：方案 A 符合微服務邊界、實作成本最低、可加 cache layer 解決流量。最終仍須與 msg-center team 對齊。

AND status = Pending AND claimed_at IS NULL；rowCount=0 即代表該 level 已被 claim、已使用或已過期。玩家可同時多開不同遊戲、campaign 可指定多遊戲 → 不靠後踢前，全面以此 FSM + CAS（DB exclusive row lock）保護。不需要 Tournament 的 StuckClaimingRetryJob，因為 FRB claim 不涉及遠端錢包呼叫，無 stuck-claim 風險。

7.1 風險 / 注意事項

  • 狀態機回溯難：TicketStatus 是 TINYINT 直存資料庫，加新值不影響歷史資料，但不可改變既有值的數字（會打爛舊 ticket 解讀）。
  • Claim idempotency：claim callback 必須 idempotent，msg-center 重送同一個 claim 不可重複處理。靠 CAS（UPDATE … SET claimed_at=NOW() WHERE id = ? AND status = Pending AND claimed_at IS NULL）原子化，rowCount=0 視同 AlreadyClaimed / Expired，不需額外 idempotency table。玩家可同時多開不同遊戲、campaign 可指定多遊戲 → 不靠後踢前，全面以此 FSM + CAS（DB exclusive row lock）保護。
  • Claim 過期邊界：玩家在 inbox 看到 claim 按鈕但票券已到 expires_at，要回傳明確錯誤，msg-center 端要能呈現「已過期」。
  • 後台操作路徑：D6 說 Suspend / Terminate / End Early 是純後台操作 — 仍需釐清後台是直接改 DB還是經 FRB API：
    • 若直接改 DB → 需 CDC + tracker 模式（類似 TournamentCampaignTracker）
    • 若經 FRB API → 在現有 API 內部加 outbox 寫入即可
  • 切換期雙寫：見 6.4 跨服務責任界線；若採雙寫過渡，需確保不會對 GameServer 重複推送同一 winning。
  • 共用 Tournament topic 的隱性耦合：D2 決定共用，要確認 msg-center 端依 event_type 而非 topic 路由，避免 Tournament 流量影響到 FRB。
