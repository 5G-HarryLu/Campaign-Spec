WALWAL 是什麼意思?

WAL = Write-Ahead Log(預寫日誌)。資料庫/儲存系統的經典耐久性技術:在真正執行操作之前,先把「我打算做這件事」持久化寫進只追加(append-only)的日誌。系統中途 crash,重啟後讀日誌即可知道哪些操作沒做完 → 重放(replay)補做,保證不遺失、不重複。

本規格是借用 WAL 概念作類比,不是實體 log 檔:

  • 「真中獎/結算」的權威記錄(WAL)= 持久化的 spin 記錄(GS 端先把 spin 標 settle_status=pending 再呼叫 SettleWin)。
  • SettleWin gRPC 或 pending-settle Stream 掉了都沒關係,掃描器會回頭掃 pending spin、重新驅動結算(重入)—— 等同 replay WAL。
  • 「WAL 不放 Valkey」= 這份耐久記錄刻意不存在 Valkey(可能會掉/重建),避免救命 log 與被保護的依賴「共命運」。
一句話:這裡的 WAL 是設計比喻 —— 用持久化 spin 記錄當不會遺失的真相來源,靠掃描器重入補做失敗結算,而非傳統 DB 引擎的實體 WAL 檔。 index.html:724, 863

Q2GS 直接呼叫 SettleEngine,有沒有更 loosely coupling 的方式?

規格已明確選擇同步 gRPC,並解釋為何不採更鬆耦合的 pub/sub:

  • 「為何不用 pub/sub(FRB 曾掉通知):GS 必須同步等金額,天然 request/response,失敗顯式可重試。」
  • retry 已定義:SettleWin 同步 gRPC、deadline 5s、立即重試 2 次;win_id = f(bet_txn_id, tier) 決定性推導,冪等在 Lua 內。
  • 耐久性不靠 pub/sub,而是「持久化 spin 記錄 + 掃描器重入」(WAL 類比)。
結論:因金額決策權在本服務、GS 必須同步拿到金額才賠付,規格判定這是本質同步的 request/response,pub/sub 反而更差。規格未提出比同步 gRPC 更鬆耦合的替代。 index.html:724, 863
需問作者:是否曾考慮「GS 先預估、事後對帳」等異步方案?此點規格未涵蓋。
Q3是否回傳金額,但由 GameServer 呼叫 DAL 寫 accounting / ledger(原本方式)?否

不是。規格明確把落帳留在本服務,只有派彩(wallet credit)才由 GS 做:

  • 落帳(win 記錄)由本服務寫:InsertJackpotWin 與 InsertOutboxMessage 同一個 OceanBase 交易(經 DAL gRPC),非 GS 寫。
  • 派彩由 GS 執行:錢包 credit 由 GS 做,金額 = 本服務結算值,wallet 側以 win_id UNIQUE 去重。
  • 資料模型已刪除 win 表的 accounting_id(「260715:代理後台不看」)—— 沒有「GS 寫 accounting/ledger」路徑。
分工:本服務原子決定金額 + 寫 jackpot_win(同交易寫 outbox);GS 只做 wallet credit 派彩。與「GS 寫 ledger」相反。 index.html:871, 875, 935
Q4公式各變數是否為設定值?「昨日 turnover」= cum_increment(t)?

公式:pool(t) = min(seed + cum_increment(t) − opened_watermark, THRESHOLD)

變數是否設定值來源

cum_increment(t)否 · 即時累積量DAL 逐筆 INCRBY input:{pool}:{tier},單調遞增

「昨日 turnover」= cum_increment(t)?

不相等,是兩條路:
  • cum_increment(t) = Valkey input key 上 DAL 即時、逐筆 累加的池貢獻(已換算後 micro-cents),驅動當下池值。
  • 「昨日 turnover」= 日終對帳用:落 jackpot_daily_increment.source_turnover_cents,再 × 累積速率。規格明講「本表不再驅動池值」。

兩者量綱與時機都不同:turnover 是注單流水,cum_increment 是換算後累積的池貢獻。 index.html:759, 982-983, 1037, 566-567, 1064-1070

Q5排程彙總是否寫進「現有的表」,由 Jackpot 讀取 + USD 換算?

大致對,但要精確區分誰算 turnover、誰換匯:

  • 寫入的表是 jackpot_daily_increment(列於本專案 10 張表內)。「是否沿用現有表」規格未明講。
  • 寫入者 = 本服務的 DailyReconJob(不是 DAL):「日終落帳(對帳錨點,PK 冪等)」。
  • USD 換算由本服務做:source_turnover_cents「本服務自 per-currency × 自有 FX 換算」,FX 版本記在 fx_versions_json。
  • 低於 min_per_day_cents 以 floor 補差。
修正描述:不是「Jackpot 讀別人算好的彙總再換匯」,而是本服務向 DAL 取昨日 turnover(per-currency)→ 本服務自己用自有 FX 換 USD → 寫進 jackpot_daily_increment。此表 v4 只當對帳錨點,不驅動池值。 index.html:705, 981, 995, 1060-1070

Q6GE 判定 + 同步 SettleWin(不可掉)+ Lua 冪等,有沒有問題?

規格自己標出的 BLOCKER / 風險

  • wallet Credit 必須以 win_id DB UNIQUE 去重(規格標紅「前置 BLOCKER」):否則 worker credit 後、ACK 前 crash 會雙重派彩,SettleWin 冪等擋不住。← 最關鍵。
  • 雙結算窗:Lua 第一動作須 SETNX settle:{win_id},否則「insert 進行中被重試 → 二次 reset」。規格已用 SETNX 封掉。
  • GS↔DAL credit 契約缺口:credit 事件需補 bet_txn_id + win_id + tier,屬 GameService.Credit、非本契約、待 GS/DAL 確認。
  • WAL 不放 Valkey:避免與被保護依賴共命運。

補充觀察(非規格,供判斷)

  • SettleWin 逾時 + 2 次重試皆失敗後,GS 側的 UX / 回補細節不在本規格,可能要 GS 團隊定義。
  • 「先到滿池、後到 seed」是執行序非中獎序,屬產品/客訴面已知取捨(已要求寫進 game info),非技術 bug。
結論:核心冪等設計(win_id 決定性推導 + Lua SETNX + OB 雙鍵 pre-check + 同交易寫 win/outbox)自洽。最大未關閉風險是 #1 wallet UNIQUE 去重與 #3 GS/DAL credit 契約 —— 兩者皆跨團隊,建議確認落實方與時程。 index.html:863, 867, 1090, 538
Q7ReconciliationJob 比對 Valkey vs DB 重算,是從 jackpot_round 判斷?是(為主錨點)

以 jackpot_round 為恢復錨點,配合 input watermark + win 重算。規格寫的重算公式來源:

「state = 上一筆 win 的 seed 錨點 + round_seq + input watermark + CDC 重放(純函數,需演練)」

對應 jackpot_round 欄位:

  • seed_microcents — 本回合 seed
  • opened_increment_watermark_microcents — cum_increment 錨點,池值合成公式用
  • round_seq / quota_remaining_at_open(Valkey 遺失時 quota = 此值 − count(wins in round))
  • clamp_overflow_microcents — 觸頂溢出累計,對帳公式顯式項、唯一記錄點
結論:不是只看 round —— round 提供錨點,其餘由 input watermark + jackpot_win 補齊,用池值公式復算後與 Valkey 比對。 index.html:883, 1028-1042
Q8「分片輪掃 + dirty-flag」的記憶體是 Jackpot service 嗎?3 個 ECS task 會不一致?不是 Jackpot

不是 Jackpot service,是 msg-center-sse 這個獨立服務的記憶體;而「3 task 不一致」在此設計下不是問題。

  • 該段標題是「msg-center SSE 容量規劃」,配置為「獨立 ECS service(msg-center-sse)+ ALB」—— 那 3 個 task 是 msg-center-sse,非 Jackpot service。
  • 記憶體 = 每個 SSE task 自己持有的那批 client 連線狀態(池值覆寫做 conflation、跑馬燈 pending 佇列)。

為何 3 task 不會「不一致」出問題

  • 每條 SSE 長連線只落在某一個 task(ALB 分流),該 task 只維護它自己承載的連線。
  • 同步靠 Redis pub/sub 扇入:每 task 訂池值 tick + 跑馬燈頻道,權威狀態在發布端,task 只把最新值覆寫進自己記憶體再輪掃推送。
  • 池值是狀態型可覆寫(conflation)、跑馬燈是廣播,都不要求 task 間強一致,晚一輪(≤5s / 1–5s 波浪式)規格可接受。
唯一要注意:規格點名的重連風暴(部署/斷網 50k 同時重連),對策 = jitter 0–30s + Last-Event-ID 續傳 + 排水 ≥300s。 index.html:909-926

A-Q1input:{pool}:{tier} 一直累加、永不重置,可以拿來做什麼?

規格對其定位的 evidence:

  • 定義:「cum_increment・DAL 逐筆即時 INCRBY」、「單調遞增、永不重置」。
  • 用途 1(合成當下池值):pool(t) = min(seed + cum_increment − opened_watermark, THRESHOLD)。永不重置 → 每 round 減去該 round 的 watermark 得淨增量,讓池值合成是純函數、可任意時點重算 —— 這正是它永不重置的設計理由。
  • 用途 2(全損重建 / 對帳):「state = 上一筆 win 的 seed 錨點 + round_seq + input watermark + CDC 重放」;ReconciliationJob 比對 Valkey vs DB。
問法建議:「單調遞增的 input 除了(a)配合 watermark 合成當下池值、(b)當全損重建/對帳錨點,還有沒有其他預期用途(例如報表、累積 turnover 趨勢)?」—— (a)(b) 規格已明載,其他用途規格未提。 index.html:566-567, 779, 759, 883
A-Q4.1opened_increment_watermark_microcents 是「超過此值才可啟動派彩」嗎?依規格:不是

根據規格,它不是派彩門檻,而是池值合成的減項基準點:

  • 定義:「開啟當下 cum_increment 錨點 — 池值合成公式用」。
  • 公式裡它是被減掉的項:seed + cum_increment(t) − opened_watermark,作用是扣掉 round 開啟前累積的 input,讓池值從 seed 起漲。
  • 派彩觸發 = GE 判定中獎 + GS 呼叫 SettleWin,與 watermark 無關;派彩金額 = SettleEngine 讀當下合成池值。
問法建議(用結論確認理解):「我理解 opened_increment_watermark 只是池值合成的基準減項、不是派彩門檻,對嗎?」 index.html:1037, 759, 724, 846, 729
A-Q4.2cum_increment(t) 永遠累積不重置?中獎 / cap reset 也不重置?

字面上:是。規格白紙黑字「cum_increment 單調遞增、永不重置」—— 中獎 reset、撞 cap reset,input key 都不歸零。

那「reset」reset 的是什麼?evidence 顯示 reset 的是池值(合成值),靠推進 watermark,不是動 input:

  • 中獎結算:「讀當下池值 = 派彩金額 → reset 到 seed」。
  • 撞頂:「池達 THRESHOLD → reset、溢位補進 seed」。
  • 每次開新 round 記一個新的 opened_increment_watermark、round_seq++。
我的推論(非規格明文):reset 機制應為「開新 round + 把新 round 的 opened_watermark 設成當下 cum_increment」→ 公式 cum_increment − opened_watermark 又從 ~0 起算 → 池值回到 seed。input 本身持續累加不動 —— input 是單調全域計數器,reset 只是移動基準線。
規格缺口:規格沒有把「reset 時 watermark 如何被設定/推進」寫成明確步驟。SettleEngine 的 Lua 只寫「reset 到 seed」,沒說它同時更新 watermark 或開新 round 的時序;Lua reset 與 RotateJackpotRound 寫新 watermark 之間的耦合未明。
問法建議:「cum_increment 永不重置,那中獎/撞 cap 的『reset 到 seed』是靠推進新 round 的 opened_watermark 到當下 cum_increment 值來達成的嗎?此 watermark 更新是在 SettleEngine 的 Lua 裡一起做,還是在 RotateJackpotRound?兩者若不同步(Lua 已 reset 但 round 未 rotate),中間的池值合成會是什麼?」 index.html:779, 729, 851, 712, 804, 867, 1037
