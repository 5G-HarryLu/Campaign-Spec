Chapter 02 · Sequence — 端到端事件故事(v4)

池值天天長大;中獎那一刻,GE 說「誰中」、Pool 說「多少」

v4 沒有逐筆抽獎了,所以故事分兩條:左線是池值怎麼長大(DAL 逐筆即時累加,每一注當下進池);右線是一次中獎怎麼處理(GE 數學判定 → GS 同步 SettleWin 拿金額 → 賠付記帳)。兩條線在 GE 的 Prob = RTP / Price 判定處交會(Price/RTP feed 落在 GS/GE 側)。

左線 · 池值怎麼長大DAL 逐筆即時累加・無輸贏

每一筆注單都被 DAL CDC 即時消費:過兩層開關就算貢獻、當下就進池。本服務不碰這條熱路徑,只在日終對帳。

一筆注單的旅程(v4:即時進池,但不被抽獎)

玩家在某支掛了 jackpot 的遊戲押下一注。這筆注單落進資料庫、由 binlog 進到 Kafka,DAL 的 CDC 即時讀到它,連問兩個問題:「這支 game 有開 jackpot 嗎?這個 operator 有開嗎?」兩關都過,就把注額換算成貢獻、當下 INCRBY 進 Valkey 對應 poolid 的池值 —— 池值是「當下、這一筆、跳一下」的即時累積。本服務不碰這條熱路徑,只在日終拿昨日 turnover 彙總落帳對帳(低於 min/day 用 floor 補差)。

真正決定輸贏的,是玩家轉動時的遊戲數學(GE)。GE 手上有本服務餵過去的兩個數字:當下池值(Price) 與這個 operator 的 RTP,用 Prob = RTP / Price 丟一個不公平的銅板。中了,GE 告訴 GS、GS 賠付,並把中獎上報本服務。本服務這時才登場:對池子做一次原子結算 —— 讀出當下池值當作派彩金額、把池 reset 回 seed(溢位補進 seed),然後落帳、連上注單號、併入 total win、發通知。

所以 v4 的分工是三方:DAL 逐筆即時把貢獻滾進池、GE 判定誰中、本服務原子決定拿多少並記帳。同一筆注單會即時墊高池值,但不會被任何抽獎迴圈掃描 —— 它中不中,是玩家轉動那一刻 GE 的事。

Chapter 04 — Judge(GE)& Settle(Pool)

GE 判定誰中、Pool 原子結算多少

v4 定案:中獎判定移到 GameServer 端的遊戲數學(GE),GS 賠付,本服務不再抽獎。本服務只在被上報中獎時,對 state:{pool}:{tier} 做一次 Lua 原子結算,決定派彩金額並 reset。金額權威在 server,不在 client 顯示。

判定 · GE 數學 ★ 定案

Prob = RTP / Price

GE 每一轉以此機率判定中獎。Price = 當下池值、RTP = 後台 by operator × 獎項設定值;Price/RTP feed 與 Prob 計算落在 GS/GE 側。GE 說中,GS 就付。config 調整接受 1 分鐘延遲。

結算 · Pool 原子

讀池 → 派 → reset

被上報中獎時,對單一 state key 跑一次 Lua:讀當下池值當金額 → reset 到 seed(溢位補 seed)→ quota−−。先到者滿池、後到者 seed,序列化在單 key。

quota · 軟限流

可負、允許同時多中

兩人可同時中(GS 都賠)。quota<1 只讓 GE 機率趨零,不是硬鎖 → quota 可為負。所以「Major 剛好 100 名」不是硬保證,PM 需知悉。

01GE 判定 → GS 同步結算(SettleWin v2,不可掉)
GE 以 Prob = RTP/Price 判定中獎 → GS 產 win_id(決定性推導 = f(bet_txn_id, tier),crash 重算永遠同一個 id)、spin 記錄先標 settle_status=pending,再呼叫本服務 SettleWin(同步 gRPC,deadline 5s,立即重試 2 次)→ 拿回結算金額才賠付。為何不用 pub/sub(FRB 曾掉通知):GS 必須同步等金額,天然 request/response,失敗顯式可重試。真 WAL = 持久化的 spin 記錄 + 掃描器重入(照 FRB ReconciliationScan 模式);pending-settle Stream 只是加速通道,掉了無所謂 — WAL 不放 Valkey,避免與被保護的依賴共命運。前置 BLOCKER:wallet Credit 必須以 win_id 做 DB UNIQUE 去重(回應帶 is_duplicate) — 否則 worker 在 credit 後、ACK 前 crash 會雙重派彩,SettleWin 冪等擋不住。
02SettleEngine 原子結算(冪等在 Lua 內)
pre-check:OB 以 win_id / (pool,tier,bet_txn_id) 雙鍵查,命中即回 is_duplicate(並校驗 bet_txn_id/member 歸屬,不符回硬錯誤,擋回錯人金額)。單一 Lua 第一個動作 = SETNX settle:{win_id} marker:已存在 → 直接回 marker 內容、不碰池(封掉「insert 進行中被重試 → 二次 reset」的雙結算窗)。否則:讀池值 = 派彩金額 → reset 到 seed(溢位補 seed)→ quota−−(可負)→ round_seq++ → FX 換算一次(記憶體快取),USD/local/fx_version/round_seq 全寫進 marker(TTL 7 天、永不主動清除)。金額恰好決定一次,之後所有路徑只搬運不重算。先到滿池、後到 seed(先到 = 先在本服務執行,非先中獎 — 寫進 game info)。Lua 之後的段落跑 detached context,不受 client cancel 中斷。
03win 落帳(DAL gRPC,連注單)
InsertJackpotWin(金額/FX 直接取 marker,不重算)與 InsertOutboxMessage 同一個 OceanBase 交易(同在 five_game_trans)— 錢到了、inbox 通知不會消失。UNIQUE(pool,tier,bet_txn_id) 兼任不變量告警(觸發 = win_id 推導被破壞,page)。RotateJackpotRound 以 round_seq 冪等,失敗交 RecoveryJob 補打。win 併入 total win。
04派彩(GS 賠付)
錢包 credit 由 GS 執行(金額 = 本服務結算值,local 金額/fx_version 取自回應,不重算);wallet 側以 win_id UNIQUE 去重。spin 回應餘額一律用 wallet 實值(不樂觀加值)+ jackpot_credit_status = credited|pending 供前端提示;成功 → member:wallet:refresh 推餘額,離線玩家由 inbox 兜住。
05通知 + 廣播
個人 inbox = 本服務寫 outbox_msg 表(經 DAL SystemService.InsertOutboxMessage,msg-center poll 表處理 — 與 FRB/Tournament 同模式,不是直接送過去,內容設計見下卡);跑馬燈事件由 GS 發到 msg-center、由其 SSE 推 client,僅限該彩金群組 operator。撞 cap 的假中獎只走跑馬燈,不落名單、不寫 outbox。
06卡單掃描 + 對帳
RecoveryJob(每 30s):age>60s 的 marker ⟷ jackpot_win 對帳補寫(只補不刪,marker 靠 TTL 清);win 存在但 round 未 rotate → 補打 Rotate。卡單掃描:payout pending 過久告警。全域對帳:credit(帶 win_id)⟷ jackpot_win 雙向比對(偵測層,期望恆 0,≥1 即 page);ReconciliationJob 比對 Valkey 池值 vs DB 重算。Valkey 全損重建:state = 上一筆 win 的 seed 錨點 + round_seq + input watermark + CDC 重放(純函數,需演練);key 命名用 hash tag {pool:tier} 防未來 cluster CROSSSLOT。

漸進式推送 = 分片輪掃 + dirty-flag(定案機制):事件進來不直接觸發發送,只更新記憶體狀態(池值覆寫 = conflation 免費內建;跑馬燈進每連線有上限的 pending 佇列)。唯一寫出者是恆速掃描器:連線 hash 進 64 shards,每 78ms 掃一個(全體 5s 掃完,~780 條/shard),有 dirty 才寫。效果:輸出恆定 10k writes/s / ~12 Mbps 平線,與事件密度完全解耦;跑馬燈在 1–5s 內波浪式亮起(會議可接受);慢客戶端 buffer 滿即跳過、下輪補最新值。中獎者本人的開獎演出走 GS 遊戲協定即時給,不受此延遲影響。 內部扇入:每 task 訂 Redis pub/sub(池值 tick + 跑馬燈頻道),負載趨近零。真正的風險是重連風暴(部署/斷網 → 50k 同時重連):client 重連加 0–30s jitter(寫進 GameClient 驗收)+ Last-Event-ID 續傳、target group 排水 ≥300s、ALB idle timeout ≥120s + 30s 心跳、ulimit nofile ≥100k、.NET Server GC;風暴後 catch-up 由輪掃自然平滑(首次拜訪補最新狀態,不補歷史)。 keyframe + increment rate 插值(10s 一個真值,前端平滑滾動 — 即規格 INCREMENT_RATE 的顯示層用途)可把頻寬與費用再降 2–5×。 ⚠ 跑馬燈頻道需 rate-limit(每 pool 每分鐘上限 N 則)+ 每連線 pending 佇列上限(如 8 則,滿丟最舊):資金失衡頻繁撞 cap 時(兩旋鈕獨立、無校核的副作用),假中獎廣播會變成風暴源。
