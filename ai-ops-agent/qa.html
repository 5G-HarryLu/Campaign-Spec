1什麼是「RUM Analyst」？

RUM = Real User Monitoring（真實使用者監控） —— 從真實使用者的瀏覽器 / App 客戶端收集的效能與錯誤遙測（頁面載入時間、前端 JS 錯誤、使用者「實際感受到」的 API 延遲、崩潰等），對比的是「伺服器端」的指標。

在本提案中，RUM Analyst 是五位並行專科代理之一，後端資料源為 SigNoz RUM，透過 SigNoz MCP 讀取。它回答的問題是：

核心職責：「這次事故是否真的傷到終端使用者？還是只在伺服器端可見？」在產出範本中可看到它的貢獻：RUM (SigNoz): No client impact detected —— 即使伺服器端延遲飆高，RUM Analyst 確認使用者端未受影響，這是與其他四位分析師（Metric / Log / Trace / Code-Change）不同的獨立證據面向。
2服務都裝了 OpenTelemetry 就會有相同的 trace_id？怎麼傳遞？

是的 —— 一個進來的請求會產生一個 trace_id，並流經所有下游服務。傳遞機制是「透過請求 header 傳播 context」，不是靠共用儲存。

步驟發生什麼
① 入口第一個收到請求的服務（如 gateway）。若請求沒有既有的 trace context，OTel SDK 會產生一個新的 trace_id（128-bit）+ span_id（64-bit）。
② 對外呼叫（注入 inject）服務 A 呼叫服務 B 時，OTel 自動把 context 注入到 outgoing header。標準為 W3C Trace Context 的 traceparent header。
③ 接收方（提取 extract）服務 B 的 OTel 提取 traceparent，看到已有 trace_id，於是把自己的 span 建成上一個 span 的子節點，並沿用同一個 trace_id。往下逐跳重複。
# W3C traceparent header 格式
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  └─ trace_id (32 hex) ─────────────┘ └ parent span_id ┘ └ flags
             version

你實際要做什麼：多數技術棧只要載入了 OTel SDK + 對應框架的 auto-instrumentation，這一切是自動的，不需手動傳 header。

唯一要注意：每一跳都必須被 instrument。若服務 B 沒被 instrument，鏈就在這裡斷掉（B 不會轉發 traceparent），其後所有下游會拿到一個全新、斷開的 trace。這正是「所有服務都必須 instrument」背後的真正前提。
3我們沒有「儲存」trace_id，Tempo 怎麼查得到？

關鍵在於：「傳播」≠「儲存」。inject/extract 只是 trace_id 在服務間旅行的方式；但每個服務另外還會把自己的 span 資料送到 Tempo。OTel SDK 做的是兩件獨立的事：

# 每個處理請求的服務，OTel SDK 都做兩件事：
(1) PROPAGATE 傳播  → inject/extract trace_id（傳給下一個服務）
(2) EXPORT 匯出     → 把本服務的 span 送到 Tempo：
     { trace_id, span_id, parent_span_id,
       service, operation, start_time, duration, attributes }

所以你不用手動把 trace_id 存進 Tempo —— OTel SDK 會自動把每個 span 匯出到 Tempo，而每個匯出的 span 本身就帶著它的 trace_id。這個匯出動作就是「儲存」。你只要把 SDK 的 exporter 指向 Tempo（通常經由 OpenTelemetry Collector）。

Tempo 如何用 trace_id 組出一條 trace

Tempo 在 ingest 時依 trace_id 把 span 分組；各 span 的 parent_span_id 則重建出呼叫順序 / 階層（誰呼叫誰）：

// 來自不同服務、亂序抵達 Tempo 的 span：
{trace_id: 7f3a, span_id: A, parent: -,  service: gateway,  2ms}
{trace_id: 7f3a, span_id: B, parent: A,  service: checkout, 2.4s}
{trace_id: 7f3a, span_id: C, parent: B,  service: wallet,   2.1s}  ← bottleneck
{trace_id: 9c1d, span_id: X, ...}   ← 另一個請求

// Tempo 依 trace_id 分組 → 組出 7f3a 的樹：
gateway (A)
  └─ checkout (B)  2.4s
       └─ wallet (C)  2.1s   ← 瓶頸 span

兩種查詢方式

方式用途
(a) 直接用 ID 查
GET /api/traces/7f3a		已知 trace_id 時的快路徑，回傳整棵 span 樹。trace_id 是它物件儲存的主鍵，所以快。
(b) TraceQL 搜尋
{ service.name="checkout" && duration>2s }		還沒有 ID 時：Tempo 對少量 span 屬性（service.name / duration / status…）建索引，先搜出符合的 trace_id，再用 (a) 撈完整 trace。
一句話：你沒有明確「儲存」trace_id，但 OTel SDK 會把每個 span（內含 trace_id）匯出到 Tempo，那個匯出就是儲存；Tempo 靠把這些 span 依 trace_id 分組來查詢與組樹。傳播與匯出是 SDK 的兩件獨立工作 —— 只想到 inject/extract 就會漏掉「匯出到 Tempo」這另一半。
4log 了 trace_id 後，就能在 OpenObserve 用 trace_id 查詢？

對，這正是重點，也是把整個關聯閉環串起來的關鍵。只要 log 行內含 trace_id 這個結構化欄位，就能在 OpenObserve（SQL 介面）查：

SELECT ts, service, account_id, level, message
FROM logs
WHERE trace_id = '4bf92f3577b34da6a3ce929d0e0e4736'
ORDER BY ts

這會回傳屬於同一個請求、跨所有服務的每一行 log —— 即 Log Analyst 的證據，並與 trace 對齊。

trace_id 怎麼進到 log 行裡（前提）

OTel SDK 透過 logging 整合 / MDC（context）暴露當前的 trace_id；你把 log 格式設定成輸出這個欄位即可。多數 logging 設定只需一行 config 就能做到 —— 你不用在程式裡手動穿針引線。

注意角色分工：request/response 的順序是由 Tempo 重建（span tree），不是從 OpenObserve 推導。OpenObserve 的角色是關聯（correlation）：「給定這條慢 trace，撈出相同 trace_id 的 log 行」，把 log 證據接到 trace 上。
5完整範例：一個 trace_id，MCP 如何把所有資訊組成一份報告

情境：使用者 account: user_88231 點「Checkout」。請求變慢並報錯。一個請求 → 一個 trace_id: 7f3a2b。以下看每個 MCP 各貢獻一塊拼圖，全部由這一個 ID 串接。

Step 0 — 因為有 instrumentation，才有這個 join key

user_88231 點 Checkout
  → gateway 產生 trace_id = 7f3a2b
  → 傳播 7f3a2b 到 checkout → wallet         (traceparent header)
  → 每個服務都把 log 行帶上 trace_id=7f3a2b
  → 每個服務都把 span 匯出到 Tempo 帶上 trace_id=7f3a2b

現在 7f3a2b 就是把一切綁在一起的唯一字串。

Step 1 — Tempo MCP：服務間的 request / response 路徑

Trace Analyst 向 Tempo 要 trace 7f3a2b，Tempo 回傳 span 樹：

trace 7f3a2b   (total 2.4s)
├─ gateway   POST /checkout        2.40s
│  └─ checkout   settleOrder()     2.35s
│     └─ wallet   WalletTransfer   2.10s   ← bottleneck span
│        └─ OceanBase  UPDATE ...  2.05s   ← 時間實際花在這

學到什麼：請求流向 gateway → checkout → wallet → DB，且 2.4s 中有 2.1s 花在 wallet.WalletTransfer。這是「在哪裡」。

Step 2 — OpenObserve MCP：哪個帳號 + 錯誤細節

Log Analyst 拿同一個 7f3a2b 查 log：

SELECT ts, service, account_id, level, message
FROM logs WHERE trace_id = '7f3a2b' ORDER BY ts
tsserviceaccount_idlevelmessage
14:05:01gatewayuser_88231INFOPOST /checkout received
14:05:01checkoutuser_88231INFOsettleOrder start
14:05:03walletuser_88231ERRORcontext deadline exceeded on WalletTransfer

學到什麼：受影響帳號為 user_88231，錯誤是 wallet 的 context deadline exceeded —— 與 Step 1 的慢 span 吻合。這是「誰 + 什麼」。（trace_id 是 join；account_id 是 log 帶的欄位。）

Step 3 — 其他 MCP 補上佐證（同時間窗 / 同 trace）

MCP / 分析師查詢回答
Grafana MCP（Metric）14:05 前後 wallet settle p99120ms → 2.4s 於 14:05 飆高
DB Health MCP（Metric）14:05 OceanBase 健康度active-session 峰值，該 UPDATE 命中 slow-log
SigNoz MCP（RUM）該流程的 client 影響無客戶端影響（僅伺服器端）
GitHub MCP（Code-Change）14:05 前剛部署了什麼PR #1234 "add sync wallet check"，14:03 部署，動到 wallet 路徑

每位分析師並行執行，各自只打自己的唯讀 MCP。

Step 4 — Reporter（經 Notifications MCP）拼成一張完整圖

Reporter 關聯所有拼圖 —— trace_id 串起 Trace↔Log，時間戳 + 動到的路徑串起 PR —— 產出：

[P1] Checkout latency — wallet settlement timing out
Account impacted: user_88231 (+ ~1,200 similar)   [from logs]
Where:  wallet.WalletTransfer 2.1s                 [Tempo trace 7f3a2b]
What:   context deadline exceeded                  [OpenObserve, trace 7f3a2b]
Metric: settle p99 120ms → 2.4s @14:05             [Grafana]
DB:     OceanBase slow-log hit on UPDATE           [DB Health]
User:   no client-side impact                       [SigNoz RUM]
Suspect: PR #1234 deployed 14:03, touches path      [GitHub] ← correlation, not proof
Confidence: High → recommend humans review PR #1234

一行心智模型

trace_id 7f3a2b  ─┬─ Tempo       → 呼叫路徑 & 時間花在哪
                  ├─ OpenObserve → 哪個帳號 + 錯誤文字   (用 trace_id join)
                  ├─ Grafana     → metric 飆高          (用時間窗 join)
                  ├─ DB Health   → DB slow-log          (用時間窗 join)
                  ├─ SigNoz RUM  → 使用者是否受影響
                  └─ GitHub      → 嫌疑 PR              (用時間 + 動到的路徑 join)
                          ↓
                  Reporter 合併全部 → 一份 incident report → 人決策
核心洞察：trace_id 是精準的 join（Trace ↔ Log，可細到單一請求 / 帳號）；其他（metrics、DB、PR）則以較鬆的時間窗 + 受影響服務 / 路徑來關聯。Agent 的全部工作就是把這些組成一個有證據的故事 —— 它從不動手修。
