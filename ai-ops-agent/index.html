AI Ops Agent — Production Incident Response

一個唯讀、只通知的多代理協調服務（Python / LangGraph）。當「錯誤在時間窗內持續累積」時自動觸發， 並行派出五位專科代理跨後端查詢與關聯，產出含證據與信心度的 incident report 推到團隊頻道 —— 並具體回答「是哪個 PR造成的」，而不只是「什麼壞了」。

Read-only · 絕不自動修復 Trigger → 報告 < 60s 每次調查 ~$0.06 MTTD / MTTR：小時級 → 分鐘級 不更動任何現有程式碼

◆ 協調與資料流（Orchestration & Flows）

四種進入點共用同一條 dedup → orchestrator pipeline，由 LangGraph 狀態機驅動五位 specialist 並行 fan-out。

1 角色與定位

跨系統關聯

把散在 Grafana、OpenObserve、Tempo、SigNoz、各 DB、GitHub 的訊號拉在一起關聯。

可行動報告

產出有證據、有信心度的 incident report，推到 incident channel。

明確不做

不自動修復 / self-healing、不自動 revert。只「指認嫌疑、附證據」，由人決策。

4 產出範本

固定格式，每一項證據都標註來源後端 —— 這是「答得出哪個 PR」的具體長相。

[P1] Checkout latency spike — spin settlement 逾時累積 Impact: ~1,200 users / 3 services · 8 min Triggered by: error-accumulation（連續 3 窗超標，趨勢未降） Root Cause: Sleipnir 結算路徑新增同步 DB 呼叫，尖峰放大延遲 Confidence: High Evidence: Metrics (Grafana): settle p99 120ms → 2.4s @14:05 Logs (OpenObserve): "ctx deadline exceeded" ×3,410 起 14:04 Traces (Tempo): trace 7f3a… 瓶頸 span = WalletTransfer 2.1s RUM (SigNoz): No client impact detected DB Health: OceanBase active-session 峰值，slow log 命中 Code Changes (GitHub):嫌疑 PR #1234 "add sync wallet check" by @dev deployed 14:03 — onset 前 2 分鐘；touched 重疊路徑 Recommendation: 1. consider reverting PR #1234（建議 — 非自動執行） 2. 尖峰時段改為非同步結算 Dashboards: Grafana · OpenObserve · Tempo · GitHub（PR 連結）

5 Guardrails & 風險

核心 Guardrails

  • 唯讀 + 只通知，無寫入生產系統。
  • Code-change 一律標示「correlation 非 causation」；revert 只是建議。
  • 每個 claim 必附具體數值 / trace ID / log / PR。
  • dedup 5 分鐘窗 + 最多 3 並行 + LLM circuit breaker + 120s timeout。
  • 後端不可達時 graceful degradation，報告標註哪些後端不可用。

主要風險 → 緩解

  • 誤指無辜 PR → 需「時間鄰近 AND 服務/路徑重疊」+ 信心分數。
  • deploy 時間缺失 → 優先 Deployments API / release tag；退回 merge time 並標註。
  • error-accum 誤報 → 持續累積閘（連續 N + 趨勢不降）；per-service 門檻。
  • GitHub rate limit → 唯讀最小權限；per-investigation 快取；403 退避降級。
  • context 溢位 → MCP 回應大小上限；先 summary 再 drill-down。
成功衡量： trigger → Telegram 報告 < 60s · 每次調查 ~$0.06（100 次/日 ≈ $6，上限 200 次/日）· 10 份人工複審準確度 · code-change 關聯命中率 · proactive 偵測 precision/recall。
