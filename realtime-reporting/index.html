即時報表架構整合提案

📖 觀念 Q&A(Sink / MV / RisingWave / OLAP）→

提案摘要
我方規劃以 RisingWave 做即時串流增量計算,並導入 OceanBase OLAP(獨立集群)作為明細查詢與歷史 BI 的服務層;Redis 負責秒級即時看板。
目標:下注寫入交易庫後約 1～2 秒內報表即可查詢,取代現行批次匯總排程(分鐘~小時延遲)。本文件說明整體架構、各服務職責、與 OceanBase 的整合介面,並列出需貴團隊協助確認的技術事項。
OceanBase OLTP →(CDC)→ Kafka → RisingWave(增量 MV)→ SINK → OceanBase OLAP(獨立集群)　;　Kafka ⇢ hotpath ⇢ Redis

為何串流計算層採用 RisingWave(相較 Apache Flink)

即時計算層在評估後採用 RisingWave 而非 Flink,主因在維運成本、穩定性與「計算即服務」的查詢便利性。我方本機 PoC 已實證下列差異。

面向Apache FlinkRisingWave(本架構採用)
開發 / 維運需撰寫 Java / Scala job,並自行打包、維護 Kafka / Sink 連接器 jar一份 SQL 即定義即時報表,免額外串流任務與連接器維運
任務存活standalone JobManager 重啟易導致 job 中斷(PoC 中曾多次發生)物化視圖持久化,服務重啟自動從 checkpoint 續傳,不掉狀態
狀態儲存本機 RocksDB + checkpoint,擴容需搬遷狀態state 落物件儲存,算 / 存分離,擴容容易
查詢方式運算結果須先 sink 至外部儲存才能查詢MV 本身即可被 SQL 查詢(計算即服務,PostgreSQL 協議)
精確去重count(distinct) 需自行維護狀態原生 exact count(distinct),增量維護
上手門檻需熟悉 Flink API / 算子模型標準 SQL + PostgreSQL 協議,團隊上手快
