1Sink 寫入 跟 一般寫入 的差別?

在本架構裡,「Sink 寫入」是串流系統(RisingWave)把計算結果「自動、持續地」推送到外部儲存的專有名詞,跟應用程式的「一般寫入」差別如下:

面向一般寫入 (App INSERT/UPDATE)Sink 寫入 (Streaming Sink)
發動者應用程式主動下 SQL,每筆都是一次 request串流引擎自己驅動,由上游資料變化觸發,無人工發送
觸發時機業務邏輯當下執行上游(Kafka / MV)一有新資料或變更就自動流出
資料形態單筆 / 小批,命令式連續資料流 (data stream),持續不斷
語義自己保證一致性、去重、重試連接器內建 upsert / 冪等 / 主鍵去重 / exactly-once
耦合App 直接綁定目標 DB透過 connector(MySQL/JDBC 協議)解耦,換目標只改設定
目的服務交易 (OLTP)把算好的結果落地到查詢層 (OLAP)
一句話: 一般寫入是「程式叫資料庫存一筆」;Sink 寫入是「串流引擎把算好的結果流,持續且冪等地灌進下游儲存」—— 在本架構即 RisingWave 透過 MySQL/JDBC Sink,把明細＋預匯總用主鍵 upsert 寫進 OceanBase OLAP 獨立集群。
2OceanBase MV 再做一層加速,MV 代表什麼意思?

MV = Materialized View(物化檢視 / 具體化視圖)。關鍵在「Materialized(物化)」這個字 —— 跟一般 View 的差別就在這:

一般 View(視圖)Materialized View(物化檢視)
資料存在哪不存資料,只存一段 SQL 定義真的把查詢結果算好、實體存成一張表(佔磁碟)
查詢時每次查都即時重跑底層 SQL直接讀已算好的結果,不用重算
速度慢(複雜 JOIN/聚合每次重算)快(換空間省時間)
代價不佔額外儲存佔儲存,底層資料變動後需「刷新 refresh」才更新

為什麼說「再做一層加速」

資料路徑是 RisingWave 算好增量結果 → Sink → OceanBase OLAP(明細＋預匯總)。OceanBase 收到的雖已是預匯總,但報表常見查詢(如「某活動近 7 天每日彙總」)若每次還要對明細做 GROUP BY 仍有成本。在 OceanBase 內再建一層 MV,把常用聚合結果預先算好、實體落地,查詢時直接讀 MV → 又快一截。所以是「在已預匯總的基礎上,再疊一層加速」。

取捨: MV 不是免費的即時 —— 它需要「刷新」。OceanBase MV 可設定刷新策略(即時/增量刷新 vs. 定時全量刷新),刷新越即時、維護成本越高。設計時要依報表能接受的延遲來選刷新模式。
3RisingWave MV 的特色?本身用的 persistent storage 是什麼?

RisingWave MV 的特色

特色說明
增量、即時更新非定時全量重算;上游一有新資料就增量自動更新,結果永遠最新(這正是與 OceanBase MV「需 refresh」最大差異)
計算即服務算好的結果直接存在 RisingWave 裡,可直接 SQL 查,不必先 sink 到外部才能查
一份 SQL 即定義CREATE MATERIALIZED VIEW ... AS SELECT ... 一句 SQL 定義即時報表,免寫 Java/Scala job、免維護連接器 jar
可疊接 (MV on MV)MV 可建在另一個 MV 之上,組成串流運算 DAG
PostgreSQL 協議相容用 PG wire protocol,可用 psql/PG driver 直接連 —— 但這只是介面相容,不代表底層是 PostgreSQL

它的 persistent storage 是什麼? → 不是 PostgreSQL

RisingWave 的 PostgreSQL 只是「連線/查詢協議」,底層儲存完全是自己的引擎:

  • 儲存引擎叫 Hummock —— 專為串流設計、基於 LSM-tree 的雲原生分散式 state store。
  • 真正的持久化層是 物件儲存(S3 協議) —— AWS S3 / GCS / Azure Blob。RisingWave 把 S3 當作唯一主儲存層:所有 internal state、MV 結果、operator 輸出、recovery log 全部落在 S3。
  • 帶來 儲存與運算分離:compute node 可彈性擴縮,狀態存於共享物件儲存,故障可恢復、成本低。

延伸:重啟/故障如何恢復?

常見誤解是「raw data 在 S3、MV 在記憶體」。正確圖像是 MV 與運算 state 本身就持久化在 S3,記憶體/本地磁碟只是 cache:

S3 (唯一主儲存,真身)  ←── Hummock LSM-tree ──→  記憶體/本地 (只是 cache)
  ├─ raw state
  ├─ MV 結果          ← MV 也在這裡,不是只在記憶體
  ├─ operator 中間狀態
  └─ recovery log

因此 compute node 重啟/故障時 不需從頭重算,直接從 S3 載回狀態 + recovery log 即可恢復,並保證 exactly-once。

注意: RisingWave 存進 S3 的是「它維持串流計算所需的 state 與 MV 結果」,不是原始資料倉儲。raw data 的 source of truth 在上游(OceanBase OLTP → CDC → Kafka);長期可供 BI/報表查詢的明細與彙總,落在 OceanBase OLAP。
一句話: RisingWave 對外講 PostgreSQL 協議(故能用 PG 工具連),對內用自研 Hummock(LSM-tree)+ S3 物件儲存做持久化,跟 PostgreSQL 的儲存引擎毫無關係。
4OceanBase OLTP 與 OLAP 的差別?

通用:OLTP vs OLAP

面向OLTP(線上交易處理)OLAP(線上分析處理)
目的處理交易:下注、扣款、寫單處理分析:報表、彙總、趨勢
典型操作大量「小」讀寫,單筆 INSERT/UPDATE,主鍵點查少量「大」查詢,掃描大量列做 GROUP BY/聚合
存取量一次碰幾筆一次掃幾百萬列
延遲要求毫秒級、高併發秒級可接受,重吞吐
資料形態最新、即時、可變歷史、累積、偏唯讀
儲存佈局列式 (row-store),利於單列存取列式儲存壓縮 + 向量化,利於大範圍掃描聚合

OceanBase 的特殊之處:HTAP

OceanBase 本身是 HTAP(Hybrid Transactional/Analytical Processing)資料庫 —— 同一套分散式引擎,既能當 OLTP 也能當 OLAP。靠的是:行列混存(同時支援 row-store 給交易、column-store 給分析)與 資源隔離(分析查詢資源與交易隔開,避免大報表拖垮線上交易)。

在本架構裡的角色(重點)

本設計刻意把兩者拆成兩個獨立集群:

OceanBase OLTP ──(CDC)──→ Kafka ──→ RisingWave ──(Sink)──→ OceanBase OLAP(獨立集群)
   交易主庫                                                    報表/分析庫
OceanBase OLTP(主庫)OceanBase OLAP(獨立集群)
角色線上業務交易的 source of truth報表 / 分析查詢的服務層
寫入來源應用程式(玩家行為、交易)RisingWave 經 Sink upsert 寫入明細＋預匯總
讀取者線上業務BI / 報表 API
為何獨立——隔離分析負載,避免大報表查詢影響線上交易效能與穩定性
一句話: OLTP＝處理交易(小而快、高併發、最新資料);OLAP＝處理分析(大掃描、聚合、可接受秒級)。OceanBase 雖是 HTAP 能兩者兼任,但本架構特意拆成兩個獨立集群,目的是負載隔離 —— 分析不拖累交易。
